# Glossário — Metrics & Telemetry

> Vocabulário canônico da feature `metrics` (telemetria local do GitPR).
> Mantido junto do [plano de execução](develop_natan/20260927_metrics_audit_plansfacts.md);
> as decisões de arquitetura vivem no [ADR-008](ADR-008-metrics-ledger.md);
> o levantamento que os originou, no [survey](../../survey/20260927_metrics_audit_surveyfacts.md).

## As quatro superfícies

O R1.3 fixou que "métricas" **não nomeia uma coisa só**. A feature tem quatro superfícies
distintas, cada uma com o seu formato, a sua durabilidade e o seu público. Confundi-las
foi a causa raiz dos defeitos G1, G2 e G3.

| Termo | Definição |
|---|---|
| **ledger de uso** | O registro canônico de telemetria: **uma linha por execução** de comando. É a superfície que responde "quantas vezes", "quanto custou" e "quem rodou". Mora em `~/.gitpr/metrics/telemetry.db` (SQLite). Substitui os arquivos de evento JSON — o nome mudou junto com a forma porque o papel mudou: antes era um diretório de arquivos soltos sem retenção (1749 arquivos, 488 KB, zero política); agora é um banco com chave primária, consulta por período e remoção por data. |
| **cache de IA** | O cache de respostas do modelo, chaveado por `md5(prompt)`. **Uma linha por prompt distinto**, não por execução — no cache hit o GitPR retorna sem regravar. É a superfície que guarda os **tokens reais**, o modelo, a duração e o autor (metadados que vêm da API do provedor), e por isso o ledger a consulta **na hora da escrita**, nunca depois. Não é, e nunca poderia ser, um registro de uso: ver *prompt distinto × execução*. |
| **log de uso (auditoria)** | O log texto-por-linha de `src/usage_log.py` em `~/.gitpr/logs/{uuid5}.log`, escrito de forma **síncrona**. É uma feature **irmã**, não uma parte da métricas: o ledger mede, o log de uso audita. Os dois foram mantidos separados (R3.4) porque as promessas são diferentes — o log promete que todo comando fica registrado, e para isso precisa de escrita síncrona e de um arquivo que se possa abrir num editor. |
| **visão humana** | O CSV e o JSON produzidos pelo export. É a **interface pública** da feature e a única que o time já lê — existe porque um banco binário não se abre num leitor de planilha. Não é o canal de transporte entre máquinas: para isso existe o *bundle*. A R3.2 registrou a proibição explicitamente: o banco é detalhe de implementação, **nunca** a interface. |

## Distinções que decidem o desenho

| Termo | Definição |
|---|---|
| **prompt distinto × execução** | A distinção que decidiu o modelo de dados inteiro. O cache colapsa execuções idênticas numa linha só (mesmo prompt → mesmo MD5 → mesmo arquivo), então cinco reviews iguais viram **uma** entrada. O ledger grava **cinco**. Qualquer agregado de uso — frequência, custo, tendência — tem de ler o ledger; ler o cache responde a uma pergunta diferente, que ninguém fez. |
| **evento** | Uma linha do ledger: um comando que rodou, com timestamp, status, provedor, modelo, tokens, duração, repo, branch, autor e módulos tocados. É **1-por-execução** por construção — é essa a propriedade que o cache não tem. |
| **módulo normalizado** | Os **dois primeiros segmentos** do caminho de um arquivo alterado (`src/fix`, `src/ui`, `docs/plans`). O corte existe por duas razões: responde "quais módulos doem mais" com o mesmo poder analítico do caminho completo, e mantém a árvore de arquivos do projeto fora do bundle que circula no merge. Arquivos de raiz (`README.md`) ficam sob o rótulo fixo `(root)`. O campo é uma **lista** e é **nullable por construção** — linter, blame e hooks rodam sem diff na mão. Sem teto de quantidade (R7.2): o tamanho do evento acompanha o tamanho do diff. |
| **origem (`source`)** | De onde a linha veio: `execution` (uma execução de verdade, observada pelo ledger) ou `cache_backfill` (reconstruída a partir do cache, e portanto **contagem de prompts distintos, não de execuções**). As duas aparecem na mesma tabela e **não** nos mesmos agregados: a reconstruída responde "o que existiu no passado", nunca "quantas vezes rodou". |
| **migração** | Absorver os arquivos de evento JSON legados para dentro do ledger, e **mover** os originais para fora de `~/.gitpr/metrics/` — nunca apagá-los. É derivável e por isso reversível à mão; a exclusão não seria. |
| **backfill** | Reconstruir histórico a partir do **cache**, marcando `source: cache_backfill`. Não é migração: a fonte é outra, o significado é outro e a precisão é menor. As duas são ofertas distintas do mesmo wizard, e o texto precisa dizer qual é qual. |
| **absorção (invariante)** | **O ledger nunca existe vazio com arquivos no disco.** Ele nasce junto com a absorção — por decisão do usuário (wizard) ou do programa (modo não-interativo) — nunca antes. É essa invariante que impede o G1 de se repetir por outra via: não existe estado em que o ledger cale o *fallback de varredura* sem ter absorvido os dados. |
| **fallback de varredura** | A leitura do cache de IA pelo dashboard **quando `telemetry.db` não existe** (R5.1). É uma **ponte de migração**, com critério objetivo de saída: no dia em que todo mundo tem banco, o caminho pode ser deletado sem quebra. Enquanto existir, os mapas de pasta de cache precisam ser um só, compartilhado — três cópias divergentes foram o defeito G2. |
| **bundle** | O **recorte** do ledger — por repo e por período — produzido por `gitpr metrics bundle` para viajar entre máquinas. É um `.db` com o mesmo schema, anexado pelo `merge` via `ATTACH` + `INSERT OR IGNORE`: a chave primária é o UUID do evento, então a deduplicação é do banco, não do código. Só o bundle escreve um binário no diretório de trabalho — o export comum não (R9.4). |
| **janela** | O período de uma consulta: `--since`/`--until`, mais o atalho `--days N` que resolve o extremo inicial para "N dias atrás" — válida para **todas** as superfícies de leitura: o resumo, o dashboard, o export, o bundle e a tool MCP. Substitui a palavra "sprint" que a documentação de conceito usava: sprint é vocabulário de um processo específico, e o GitPR não tem — nem deveria ter — noção de qual processo o time usa. Uma janela explícita serve a Scrum, Kanban e a quem não usa nenhum dos dois. |
| **custo** | A conversão de tokens em dinheiro, por uma tabela de preços **embutida**, cotada em USD, com override por `.env` e moeda configurável. É sempre uma **aproximação**: os preços mudam no tempo, e converter tokens antigos pela tabela de hoje não reconstrói o que foi pago. A documentação declara isso em vez de esconder. Provedor local (ollama) custa zero; e um total que deixou modelos sem tarifa sai como `Total (parcial)` em vez de parecer a conta inteira. |
| **exceção honesta** | `ScmNotSupportedError` levantado quando uma forja genuinamente não sabe fazer algo — nunca um resultado inventado. O padrão já existe no projeto: `supports_reviewable_diff = False` no Azure DevOps barra a revisão remota **antes** de qualquer chamada de rede; `supports_merged_dates = False` no Bitbucket declara o mesmo sobre datar um merge, e a secção de ciclo diz isso sem gastar uma chamada. Aplicado aqui à listagem de PRs por estado e período nos quatro provedores (R9.3): cada um **traduz** o estado canônico para o vocabulário da sua forja e descarta o que veio além do pedido — o GitHub não tem estado `merged`, então pede `closed` e fica com as linhas que têm `merged_at`; e como a listagem vem ordenada por atualização decrescente, a paginação para assim que a janela ficou para trás, em vez de varrer o histórico inteiro. Onde a forja não souber listar, o provedor levanta a exceção — a alternativa, varrer tudo e filtrar em memória, queima rate limit e mente sobre o custo da operação. |
| **wizard de migração** | A TUI que cria o ledger e oferece as duas absorções. Abre **só em invocação interativa e só quando há o que importar** (R8.1) — é um wizard de *migração*, não de setup: quem acabou de instalar o GitPR nunca o vê, porque não há passado para absorver. |
| **escrita síncrona** | A promessa de durabilidade do ledger. Substitui a thread daemon fire-and-forget (G3), que perdia a linha sempre que o processo encerrava antes de a thread ser escalonada — o caso exato dos hooks, cujo processo inteiro é "inicia → dispara → sai". O `src/usage_log.py` já documentava esse risco no próprio docstring e por isso sempre escreveu de forma síncrona. |

## Chaves de configuração (dotenv plano, `~/.gitpr/.env`)

| Chave | Significado |
|---|---|
| `GITPR_METRICS_CURRENCY` | Moeda em que o custo é reportado (default `USD`, que é a moeda em que a tabela embutida é cotada; configurar outra afasta a tabela embutida para todo modelo sem tarifa própria). |
| `GITPR_METRICS_PRICE_<MODEL>_INPUT` / `_OUTPUT` | Override da tabela de preços embutida, por modelo, em unidades por milhão de tokens. `<MODEL>` é o nome do modelo em maiúsculas, com cada sequência que não seja letra ou dígito colapsada num `_`. **As duas tarifas são obrigatórias**: um modelo com só uma delas é reportado em tokens, porque tarifar a outra metade a um zero não configurado subestimaria a conta. Existem porque preço de modelo muda mais rápido do que release de CLI. |
| `GITPR_METRICS_RETENTION_DAYS` | **Não existe, deliberadamente.** Não há expiração automática (R7.3): o histórico do ledger é a verdade de custo e de time, e apagá-lo por calendário mudaria sozinho a resposta de "quanto gastamos no ano". A remoção é o `prune`, explícito e com confirmação. |

## Notas de fidelidade

- **O cache não é um ledger, e a diferença não é de formato.** `save_cached_response()` grava em `{md5(prompt)}.json`, e o caminho de cache hit em `src/core.py:976-989` retorna **antes** de regravar. Não há conserto de schema que faça o cache contar execuções: a chave primária dele *é* o conteúdo do prompt.
- **A metainformação boa nasce no cache.** Tokens reais, `duration_ms`, provedor e modelo são montados em `src/ai_providers.py:139-213` a partir do `usage_metadata` do provedor e injetados em `response._telemetry_meta`. O ledger os copia **na hora da escrita** — o join difuso por minuto que existia antes (`enrich_metrics_from_cache()`) nunca casava para `fullreview` e `filereview`, porque três cópias do mapa de pastas de cache divergiam entre si (G2). Copiar na escrita elimina a classe inteira do problema.
- **O `config.json` de UUIDs exportados deixa de existir.** Ele era a origem do G1: `export_metrics()` montava a lista de arquivos de **todos** os donos, filtrava os eventos por repo, e gravava os UUIDs de todos no estado global — exportar no repo A marcava os eventos do repo B como exportados, permanentemente e em silêncio. Com o ledger, o controle de exportação é uma consulta, não um arquivo de estado.
- **`show_metrics_summary()` conta `*.json` recursivamente** (`src/metrics.py:452-460`), então a pasta de arquivos legados precisa ficar **fora** de `~/metrics/` — dentro, o G7 dobraria em vez de sumir.
- **Duas rotas para achar PRs, deliberadamente.** O motor de release sobe a ancestralidade local dos merge commits (precisa de atribuição por commit e roda offline); a métrica de ciclo usa a listagem da API (precisa do período inteiro e das datas autoritativas da forja). São trabalhos diferentes, e convergir forçaria o changelog a exigir rede.
- **O G15 não é regressão, e o conserto não é retroativo.** `release_engine.py:429` roda `git log --no-merges` e `_extract_pr_number()` só lê sufixo de squash. Num repositório que faz merge commit — este — `pr_number` era `None` **por construção**, e o segmento `· [#n](url)` documentado no CLAUDE.md nunca apareceu em nenhum changelog publicado. A correção (R9.1) é uma **segunda passada** `git log --merges` sobre o mesmo range, que monta `hash → número do PR` por `rev-list <merge>^1..<merge>^2`: os bullets continuam um por commit, agora com o link. Um merge que não é pull request (`Merge branch 'main' into …`) não empresta número nenhum, um commit alcançável por dois merges fica com o mais próximo, e **as secções já publicadas do CHANGELOG não são reescritas** — só uma secção nova nasce com links.
