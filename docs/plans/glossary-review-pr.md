# Glossário — `gitpr review-pr`

> Vocabulário canônico da feature `gitpr review-pr` (revisar um pull request já aberto na forge, sem checkout da branch).
> Mantido junto da [spec](20260917_skill_gitpr_review_pr_spec.md), do [plano](20260917_skill_gitpr_review_pr_spec_plan.md) e do [levantamento](../survey/20260917_skill_gitpr_review_pr_surveyfacts.md); a lista de desvios aprovados vive no [ADR-005](ADR-005-review-pr-subcommand.md).

## Termos de domínio

| Termo | Definição |
|---|---|
| **review de PR remoto** | Revisar um pull request que já existe na forge buscando o seu diff pela API. O objeto da revisão é o **PR**, não a árvore local: o comando não faz checkout, não faz fetch e não lê o working tree. É o modo de quem foi convidado a revisar o PR de outra pessoa. |
| **diff revisável** | Um diff unificado de verdade — seções `diff --git a/…` com `@@` hunks —, e não uma lista de arquivos alterados. É o insumo obrigatório do review: sem ele não há o que a IA revise, nem o que o chunker divida, nem o que o filtro de excludes recorte. Azure DevOps **não** serve diff revisável (a API devolve `changes` com contagem de linhas); GitLab serve, mas só depois que o provider sintetiza os cabeçalhos (§abaixo). |
| **capacidade de diff** | `supports_reviewable_diff`, atributo de classe da `ScmProvider` (`True` na ABC, `False` no Azure DevOps). É declarada **pelo provider** e checada **antes de qualquer chamada de rede** — a recusa mais barata que existe, e a razão de um provider novo declarar a própria resposta em vez de o chamador adivinhar. |
| **rede de segurança do conteúdo** | A checagem de que o texto recebido é mesmo um diff, executada **depois** da capacidade e **antes** da IA. Existe porque uma flag é uma promessa: um provider que declare `supports_reviewable_diff` e responda com prosa é pego aqui, e não revisado como se fosse código. |
| **`DiffSource`** | O contrato de proveniência do diff revisado: origem (`LOCAL` / `REMOTE_PR`), conteúdo, identificador, número do PR, `RepoRef` e as duas branches. **Não entra no motor de review** — o motor continua recebendo uma string de diff, porque já era agnóstico à origem —, mas é o que nomeia o relatório, escopa o cache e permite que a tool MCP diga de onde veio o que revisou. |
| **origem do diff** | `DiffOrigin`: `LOCAL` (working tree ou branch vs. remota) ou `REMOTE_PR` (API da forge). É a única diferença de fundo entre os fluxos: o resto do pipeline — prompt, skill, cache, linter, renderização — é literalmente o mesmo código. |
| **escopo de cache** | `::diff-source::pr-<n>`, acrescentado **somente à chave MD5** e nunca ao prompt enviado à IA. Sem ele, um review remoto de uma branch que por acaso está em checkout local geraria um prompt byte a idêntico ao do review local e seria respondido pelo cache errado. Com escopo vazio (`""`, o que os fluxos locais passam) a chave é idêntica à de sempre: **zero invalidação de cache existente**. |
| **smart excludes (remoto)** | Os mesmos padrões de sempre (`~/.gitpr/conf/gitpr.smart-excludes.json`), aplicados de outra forma: git os aplica como pathspecs `:(exclude)` em todo diff local, mas um diff vindo da API nunca passa pelo git, então o recorte acontece em Python, seção por arquivo (`filter_excluded_sections`), via `fnmatch`. Os arquivos descartados são **nomeados** num aviso. |
| **diff gravado no registro** | O campo `diff` de topo do registro de cache, gravado pela chamada de review. É a **fonte de verdade** que o `gitpr fix` passou a preferir: um review remoto não tem árvore local que o reproduza, e mesmo um `-f` local recalculado depois só aproxima a branch daquele dia. Registros antigos não têm o campo e caem no recálculo. |
| **comentário** | A publicação opcional (`--post-comment`) do review no PR: review + alertas do linter + **rodapé de proveniência**. Sempre um comentário **novo** (nada é editado por cima), e sem SHA de commit — `PullRequestResult` não carrega um, e inventá-lo num comentário público seria pior do que omiti-lo. O rodapé diz "AI-generated" porque quem lê o PR pode não ter rodado o comando. |
| **estado aberto** | O único estado em que um PR é revisável, escrito de forma diferente em cada forge: GitHub `open`, GitLab `opened`, Azure `active`, Bitbucket `OPEN`. Comparado em caixa baixa, uma lista cobre os quatro. Um provider que **não reporta** estado é deixado passar — recusar por um campo que ele nunca prometeu seria pior do que confiar no diff. |
| **cabeçalho sintético (GitLab)** | As três linhas (`diff --git a/… b/…`, `--- a/…`, `+++ b/…`) que o provider GitLab **fabrica** antes de cada hunk, porque a API devolve `changes[].diff` como hunk puro e o caminho do arquivo em campos separados (`old_path` / `new_path`). Sem elas, a IA receberia hunks órfãos, o chunker não acharia onde dividir e o filtro de excludes não teria caminho por onde recortar. |
| **`overflow` (GitLab)** | Flag da API do GitLab avisando que o diff do arquivo foi **truncado** por exceder o limite de tamanho. Um diff truncado não é um diff: o provider levanta erro e o revisor é mandado revisar aquele merge request localmente, em vez de receber meia revisão publicada como se fosse inteira. |
| **review sem `checkout`** | O contrato de superfície do comando: subcomandos **não** chamam `check_unstaged_files` (o diff não vem da árvore) e o comando **não** checa a árvore de trabalho. Não é economia de uma chamada: verificar arquivos não preparados numa execução que não os lê seria uma pergunta sem consequência. |
| **tool MCP read-only** | `review_remote_pr`, a 14ª tool: revisa e devolve o resultado, **sem** `post_comment` e **sem** gravar `.txt`. Uma tool que um agente chama por conta própria não pode ter como escrever no PR de alguém — mesmo precedente do `list_fix_candidates`. |
| **skill `.gitpr.review.md`** | A **mesma** instrução de sistema do review local. Não existe skill específica do remoto: um review que lesse diferente conforme a origem do diff anularia o motivo de compartilhar o motor. |

## Notas de fidelidade

- **O motor não mudou de assinatura.** `generate_pr_content` ganhou apenas dois parâmetros **opcionais** com defaults que preservam o caminho local byte a byte: `cache_scope=""` (chave MD5 idêntica à de hoje) e `store_diff=False`. Nada de `DiffSource` dentro do motor.
- **Nenhuma chave de configuração nova.** O comando reusa `OUTPUT_FILE_NAME_REVIEW`, a forge do `--init` e o `DEFAULT_AI_PROVIDER`. O que não existe como configuração não foi inventado.
- **`provider` no código é o do AI; o da forge chama-se `scm_provider`.** Dois conceitos diferentes que responderiam ao mesmo nome na mesma assinatura — só o da IA ficou abreviado (`ai_provider`).
- **O `get_pull_request` é concreto na ABC, não `@abstractmethod`.** Todos os quatro providers o implementam, mas o default que levanta `ScmNotSupportedError` mantém subclasses de terceiros e o teste de contrato compilando — mesmo padrão do `create_release`.
- **`list_open_pull_requests` continua sem paginar** nos quatro providers. É por isso que o review remoto resolve o número **direto** (`get_pull_request`): filtrar uma página só por número erra os PRs mais antigos e não distingue mesclado de inexistente. O defeito de paginação em si é pré-existente e ficou fora do escopo.
- **ADR-002 está duplicado** em `docs/plans/` (`ADR-002-gitpr-release-subcommand.md` e `ADR-002-reviewer-suggestion.md`); por isso este é o **ADR-005**.
